This all started when I began digging into I/O multiplexing. By default, socket functions like read() and accept() are blocking. That means your thread just sits there waiting for the operation to complete before it can do anything else. When you are writing a network server that might handle hundreds or thousands of clients at the same time, having one idle or slow connection stall the whole process completely ruins responsiveness.

To solve that without spawning a heavy thread for every single socket, Linux gives us I/O multiplexing: select(), poll(), and epoll(). This project is built around poll().

1 · Why poll() over select()

select() was the first standard way to multiplex sockets, but it has some annoying limitations. The most infamous is FD_SETSIZE, which caps the maximum file descriptor you can monitor to 1024. On top of that, select() modifies the bitmask in-place, meaning on every single iteration of your event loop, you have to re-copy and re-initialize the descriptors you care about.

poll() fixes both of those headaches. Instead of bitmasks, you pass a simple array of struct pollfd: 

struct pollfd {
    int   fd;       /* file descriptor to watch */
    short events;   /* bitmask of events we care about (POLLIN, POLLOUT) */
    short revents;  /* bitmask of events returned by the kernel */
};

There is no arbitrary 1024 limit because it's just an array whose size you control. And because events (what you request) and revents (what actually happened) are separate fields, the kernel never overwrites your configuration. You can leave the array in place across loop iterations and only inspect revents.

2 · The "Simple" Echo Server Problem

To get comfortable with poll(), I wrote an echo server. On the surface, an echo server sounds like the simplest project imaginable: read whatever bytes the client sends to you, and write them right back out.

In a blocking single-client setup, that takes about ten lines of code. But doing it concurrently on a single thread with non-blocking sockets and poll() was actually quite a challenge. The moment sockets are non-blocking, every assumption about I/O breaks:

  • A read() can return fewer bytes than you asked for, or return EAGAIN if no data has arrived yet.
  • A write() can return fewer bytes than you requested (a partial write) because the socket's kernel send buffer is full, and trying to write the rest immediately will block or drop data.
  • You cannot just sit in a while loop waiting for the write to finish, because that blocks all other connected clients.

3 · Designing the Client State Struct

The first problem was figuring out how to store client buffers and track progress without leaking memory or mixing up data. Each client needs its own buffer and offsets. So I created a dedicated struct client: 

#define MAX_CLIENTS 1020
#define BUF_SPACE   4096

struct client
{
    int fd;
    char buf[BUF_SPACE];
    size_t len;  /* bytes currently in buf          */
    size_t sent; /* how many of those were written  */
};

struct pollfd fds[MAX_CLIENTS];
struct client Clients[MAX_CLIENTS];
nfds_t nfds = 0;

Here is why each field matters:

  • fd: The socket file descriptor associated with this client slot.
  • buf: A 4 KB buffer holding the data received from the client.
  • len: The total number of valid bytes currently sitting in buf waiting to be echoed.
  • sent: How many of those len bytes have actually been written to the socket so far.
why tracking 'sent' is necessary In non-blocking mode, if a client sends 4000 bytes and you call write(), the kernel might only accept 1500 bytes before filling the TCP socket send buffer. sent records that 1500 bytes went out, so the next time poll() tells us the socket is writable, we write starting at buf + sent for the remaining len - sent bytes instead of resending from byte 0.

4 · Managing Read vs. Write State

After setting up the struct, the next step was managing whether each client is currently in a "read" state or a "write" state:

1. Read state: When the buffer is empty (len == 0), the client is waiting for new input. We set fds[i].events = POLLIN so the kernel notifies us when incoming data arrives. 

int on_client_readable(nfds_t i)
{
    ssize_t nr = read(fds[i].fd, Clients[i].buf, BUF_SPACE);
    if (nr > 0)
    {
        Clients[i].len = (size_t)nr;
        Clients[i].sent = 0;
        fds[i].events = POLLOUT;  /* switch to write state */
        return 0;
    }
    if (nr == 0)
    {
        return -1;  /* client disconnected cleanly */
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK || errno == EINTR)
    {
        return 0;   /* no data ready right now, keep listening */
    }
    return -1;      /* read error */
}

2. Write state: Once read() gives us bytes, we immediately flip fds[i].events = POLLOUT. We do not try to read anything more from this client until we have finished echoing back what we just received. 

int on_client_writable(nfds_t i)
{
    ssize_t nw = write(Clients[i].fd, Clients[i].buf + Clients[i].sent,
                       Clients[i].len - Clients[i].sent);
    if (nw >= 0)
    {
        Clients[i].sent += (size_t)nw;
        if (Clients[i].sent == Clients[i].len)
        {
            /* entire buffer has been written back out */
            Clients[i].len = 0;
            Clients[i].sent = 0;
            fds[i].events = POLLIN;  /* switch back to read state */
        }
        return 0;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK || errno == EINTR)
    {
        return 0;
    }
    return -1;
}

Once Clients[i].sent == Clients[i].len, the echo is complete. We reset both counters back to 0 and switch events back to POLLIN. This clean flip prevents busy-looping on POLLOUT when there is nothing to send.

5 · Non-Blocking Accept Loop

The listening socket is placed at fds[0] with POLLIN. When fds[0].revents & POLLIN triggers, it means there is at least one new connection waiting in the accept queue.

Because multiple clients can connect in the same poll interval, calling accept() just once would leave the rest hanging until another connection arrives. So you have to drain the accept queue inside a non-blocking loop: 

void on_listner_ready(int listner)
{
    for (;;)
    {
        int fd = accept(listner, NULL, NULL);
        if (fd == -1)
        {
            if (errno == EAGAIN || errno == EWOULDBLOCK)
            {
                return;  /* accept queue is completely drained */
            }
            if (errno == EINTR || errno == ECONNABORTED)
            {
                continue;
            }
            perror("accept");
            return;
        }
        set_nonblocking(fd);
        if (add_client(fd) == -1)
        {
            close(fd);
        }
    }
}

Every accepted descriptor is immediately marked O_NONBLOCK with fcntl() and registered into our fds and Clients arrays.

6 · Swap-with-Last Compaction & Backwards Loop

poll() requires a dense array of size nfds. If client #12 in an array of 50 clients disconnects, leaving a hole is messy, and shifting every subsequent element left by one with memmove takes \(O(N)\) time.

The classic solution is swap-with-last removal: copy the very last element in the array into the slot of the dead client, then decrement nfds: 

void remove_client(nfds_t i)
{
    if (i == 0) return;  /* never remove the listening socket */

    close(fds[i].fd);
    if (i != nfds - 1)
    {
        fds[i] = fds[nfds - 1];
        Clients[i] = Clients[nfds - 1];
    }
    --nfds;
}
the forward-loop indexing trap If you iterate forward (for (int i = 1; i < nfds; i++)) and remove client i, whatever client was at the end of the array is swapped into slot i. On the next iteration, i increments to i + 1, which completely skips checking the newly-swapped client in this turn!

The fix is simple once you realize it: iterate through the clients backwards: 

for (int i = (int)nfds - 1; i > 0; i--)
{
    if (fds[i].revents == 0) continue;

    int dead = 0;
    if (fds[i].revents & POLLNVAL)
        dead = 1;
    else if (fds[i].events & POLLOUT)
        dead = (on_client_writable((nfds_t)i) == -1);
    else
        dead = (on_client_readable((nfds_t)i) == -1);

    if (dead)
    {
        remove_client((nfds_t)i);
    }
}

When you iterate backwards, removing slot i replaces it with something from the tail that has either already been processed or was the item being dropped. The elements before it (which haven't been visited yet) remain completely untouched.

7 · Corner Cases: SIGPIPE & POLLNVAL

A couple of Unix networking quirks had to be handled explicitly:

  • signal(SIGPIPE, SIG_IGN): If a client unexpectedly closes their connection while the server is trying to write() to it, the kernel's default behavior is to send a SIGPIPE signal to your process. That kills the whole server instantly without a traceback. Calling signal(SIGPIPE, SIG_IGN) at startup makes the write() call return -1 with errno == EPIPE instead, allowing the server to clean up the client and keep running.
  • POLLNVAL handling: If a file descriptor is closed out from under the poll set or is somehow invalid, poll() flags POLLNVAL in revents. The loop checks for this explicitly and purges the slot immediately.
