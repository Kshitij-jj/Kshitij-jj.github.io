Blocking Sockets

Understanding synchronous socket communication in networking

⬅ Writeups

Introduction

Sockets are a fundamental abstraction provided by the operating system that allow communication between two processes over a network.

Any data sent between devices over a network—such as messages, requests, or file transfers—uses sockets as the communication interface.

In simple terms, a socket is one endpoint of a two-way communication channel between two programs running over a network.

What is a Blocking Socket?

A blocking socket is a socket mode where system calls like accept() and recv() pause program execution until the operation completes.

For example, recv() will block the program until data is received from the other side. Similarly, accept() blocks until a new client connects.

This means the program cannot perform any other task while waiting for an event to occur.

Simple TCP Server and Client

A basic blocking socket program consists of a server and a client. The server waits for a connection, and the client connects and sends data. 


// Server (blocking)
socket()
bind()
listen()

client = accept()   // blocks until client connects
recv(client)        // blocks until data arrives
send(client)

This setup works well for a single client connection.

How Execution Flow Works

In blocking mode, the server executes in a linear fashion and waits at specific system calls. 


Client -----> Server

accept()  → waiting for connection
recv()    → waiting for data

The execution stops at each blocking call until the kernel returns control.

Why Blocking Sockets Are Useful

Blocking sockets are simple, predictable, and easy to implement. The flow of execution is linear, which makes debugging and learning much easier.

This is why most beginners start networking with blocking sockets.

The Problem with Blocking Servers

The main limitation appears when multiple clients try to connect at the same time.

Since the server is blocked on one client at a time, it cannot handle other clients until the current operation finishes.

This leads to poor scalability in real-world applications.

Handling Multiple Clients

A common solution is to use threads or processes, where each client is handled independently.

However, this introduces new problems such as higher memory usage, context switching overhead, and reduced scalability when the number of clients increases.

Why This Becomes a Problem at Scale

In real-world systems like web servers, chat servers, and scanners, thousands of clients may connect simultaneously.

A blocking approach cannot efficiently handle this load because the server spends time waiting instead of doing useful work.

What Comes Next?

Blocking sockets are simple and useful, but they do not scale well.

This raises an important question: Can we avoid waiting while still handling multiple clients?

To solve this, we move to non-blocking sockets.
