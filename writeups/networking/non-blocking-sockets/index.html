Non-Blocking Sockets

Understanding asynchronous socket communication in networking

⬅ Writeups

What is a Non-Blocking Socket?

A non-blocking socket is a socket mode where system calls such as accept() and recv() do not pause program execution while waiting for an event.

Instead of blocking until data arrives or a client connects, these system calls return immediately.

If no event is currently available, the calls return -1 and set errno to EAGAIN or EWOULDBLOCK.

This allows the program to continue executing other tasks instead of being stuck waiting on a single socket operation.

How Non-Blocking Behavior Works

In blocking mode, the kernel pauses execution until an operation can complete.

In non-blocking mode, the kernel immediately returns control back to the program.

If no event is ready:

  • recv() returns -1 with EAGAIN or EWOULDBLOCK
  • accept() returns -1 with EAGAIN or EWOULDBLOCK

The program must check again later instead of waiting automatically.

Creating a Non-Blocking Socket

Non-blocking behavior is usually enabled using fcntl(). 


// Make server socket non-blocking
int flags = fcntl(server_fd, F_GETFL, 0);
fcntl(server_fd, F_SETFL, flags | O_NONBLOCK);

socket();
bind();
listen();

while (1) {

    client_fd = accept(server_fd,
                       (struct sockaddr *)&client_addr,
                       &addr_len);

    if (client_fd == -1) {
        // No pending connection
        continue;
    }

    // Make client socket non-blocking too
    int client_flags = fcntl(client_fd, F_GETFL, 0);
    fcntl(client_fd, F_SETFL, client_flags | O_NONBLOCK);

    recv(client_fd, buffer, sizeof(buffer), 0);
}

Unlike blocking sockets, the server continues running even when no client connection or incoming data is available.

Blocking vs Non-Blocking


Blocking:
  accept() → waits
  recv()   → waits

Non-blocking:
  accept() → returns immediately
  recv()   → returns immediately

Blocking sockets pause execution until work becomes available.

Non-blocking sockets never pause execution automatically; the program must repeatedly check whether sockets are ready.

Why Non-Blocking Sockets Are Used

Non-blocking sockets allow a single thread to manage multiple connections without getting stuck waiting on any one operation.

This improves responsiveness and forms the foundation of event-driven networking systems.

The Problem with Pure Non-Blocking I/O

Since non-blocking system calls return immediately, the program must continuously check sockets in a loop. 


while (1) {

    accept(server_fd, ...);

    recv(client_fd, buffer, sizeof(buffer), 0);

    // Loop repeats immediately again and again
}

Because no system call blocks execution, the CPU keeps running the loop repeatedly even when no network activity exists.

This behavior is called busy waiting or busy polling.

In such cases, the program may consume nearly 100% CPU usage while doing no useful work.

Why is usleep(1000) Used?

If you check the server code in the repository, you may notice the following statement: 


usleep(1000);

usleep(1000) pauses the current thread for 1000 microseconds, which equals 1 millisecond.

This small delay prevents the loop from running continuously at maximum speed and reduces unnecessary CPU usage.

Without this delay, the program would repeatedly execute the loop millions of times per second because no operation inside the loop blocks execution.

Although this reduces CPU usage slightly, manually polling sockets in a loop is still inefficient and does not scale well.

What Comes Next?

Non-blocking sockets solve the waiting problem, but they introduce a new issue: inefficient CPU usage caused by constant polling.

Instead of manually checking every socket repeatedly, modern networking systems use I/O Multiplexing.

With techniques such as select(), poll(), and epoll(), the kernel notifies the program exactly when sockets become ready for reading or writing.

This eliminates unnecessary polling and allows applications to handle many connections efficiently.
