1 · Raw DNS Resolver from Scratch

I wanted to see how DNS packets are built at the byte level without having a library do it behind the scenes. In C, you would define a packed struct and cast pointers over a buffer. In Python, you can achieve the exact same control using ctypes.BigEndianStructure so that multi-byte fields are automatically encoded in network byte order. 

import ctypes

class DNS_HDR(ctypes.BigEndianStructure):
    _fields_ = [
        ("ID", ctypes.c_ushort),
        ("FLAGS", ctypes.c_ushort),
        ("QDCOUNT", ctypes.c_ushort),
        ("ANCOUNT", ctypes.c_ushort),
        ("NSCOUNT", ctypes.c_ushort),
        ("ARCOUNT", ctypes.c_ushort)
    ]

For the query, the header flags are set to 0x0100 (standard query with recursion desired, RD=1). But the tricky part of building a DNS query is the question section (QNAME). You can't just send "google.com" as a normal string. DNS encodes domain names as a sequence of length-prefixed labels: length byte, followed by the label bytes, terminated with a null byte (0x00).

So "google.com" turns into b"\x06google\x03com\x00". I wrote a manual encoder to convert domain strings into raw QNAME bytearrays: 

def qname_get(domain_name):
    if domain_name.endswith("."):
        qname = bytearray(len(domain_name.encode("ascii")) + 1)
    else:
        qname = bytearray(len(domain_name.encode("ascii")) + 2)
    i = 0
    for label in domain_name.split("."):
        if len(label) == 0:
            break
        label_len = len(label.encode("ascii"))
        qname[i] = label_len
        i += 1
        qname[i : i + label_len] = label.encode("ascii")
        i += label_len
    qname[i] = 0
    return qname

After the QNAME, you append 2 bytes for QTYPE (0x0001 for Type A) and 2 bytes for QCLASS (0x0001 for Class IN). Then send it off via a standard UDP datagram socket to 8.8.8.8:53.

2 · Name Compression & Pointer Masking (0xC0)

Sending the query is straightforward, but parsing the response is where DNS gets tricky because of RFC 1035 message compression. To save bandwidth, DNS responses don't repeat domain names. Instead, if a label begins with the two high bits set (11xxxxxx in binary, or 0xC0 as a mask), it indicates an offset pointer back to where the domain name was previously defined in the packet.

the compression trap If you assume every label is preceded by an ordinary length byte, your parser will blow up the moment it reads an answer record. A length of 0xC0 would look like a 192-byte label, which immediately runs past the packet buffer or triggers bounds checks. You have to check whether (byte[i] & 0xC0) == 0xC0. If it is, the pointer is two bytes long (the 14 remaining bits give the offset), and you advance your parsing cursor by 2 bytes. 
# Walking past the question and answer names
while i < pkt_size and byte[i] != 0:
    if (byte[i] & 0xC0) == 0xC0:
        # It's a compression pointer (2 bytes total)
        i = i + 2
        break
    else:
        if byte[i] > 63:
            return  # Invalid label length
        else:
            i = i + byte[i] + 1
else:
    i = i + 1

Once you walk past the question record (QNAME + 4 bytes for QTYPE/QCLASS) and the answer record header (NAME + TYPE + CLASS + TTL, totaling 10 bytes), you reach RDLENGTH (2 bytes) and then the actual RDATA payload. For an A record, RDLENGTH is 4 bytes, representing the 32-bit IPv4 address, which we format using socket.inet_ntoa().

3 · Edge Cases: NXDOMAIN, Timeouts, and Validation

I tested three specific failure and edge cases against Google's resolver (8.8.8.8):

  1. Successful resolution: Resolving standard domains like google.com and checking that the returned IP matched.
  2. NXDOMAIN: Querying non-existent domains. The server returns a response with ANCOUNT == 0 and an RCODE indicating non-existence. The parser checks if hdr.ANCOUNT == 0: return cleanly without crashing.
  3. Resolver timeout: Testing against an unreachable IP address to ensure timeout handling worked.
avoiding blanket exceptions Instead of wrapping everything in a lazy except Exception: block, I set an explicit 10-second timeout on the socket (sock.settimeout(10)) and caught socket.timeout explicitly. That way, a genuine network timeout doesn't get masked as a parsing failure or code bug.

4 · Building the Vulnerable Target (vuln.c)

The second part of the block was binary exploitation in Python. To understand format-string vulnerabilities and memory leaks, I wrote a minimal vulnerable program in C (vunl.c): 

#include <stdio.h>

void vunl()
{
    char buf[64];
    long secet = 0xdeadbeef;
    printf("Buf: %p, Secret: %p\n", buf, &secet);
    fgets(buf, sizeof(buf), stdin);
    printf(buf);  /* vulnerable: format string directly from user input */
}

int main()
{
    setvbuf(stdout, NULL, _IONBF, 0);
    vunl();
    return 0;
}

The bug is on line 9: printf(buf) instead of printf("%s", buf). If the input contains format specifiers like %lx or %p, printf interprets them as instructions to fetch and print arguments from memory according to the calling convention, even though no additional arguments were passed.

5 · System V Calling Convention & Register Exhaustion

To predict what printf actually prints, you have to know the x86-64 System V AMD64 ABI calling convention:

  • 1st argument: rdi (the format string pointer itself)
  • 2nd argument: rsi
  • 3rd argument: rdx
  • 4th argument: rcx
  • 5th argument: r8
  • 6th argument: r9
  • 7th argument and beyond: pushed onto the stack in reverse order

This means the first 5 specifiers (positions 1 through 5) leak the contents of CPU registers (rsi through r9). They do not read the stack at all.

the register exhaustion threshold Specifier 6 is the exact transition point where register arguments are exhausted and printf begins walking up the stack frame. Starting from the 6th position, you are leaking stack memory.

6 · Diagnosing the stdio Buffering Deadlock

When I first started writing the exploit script using pwntools (p = process("./vunl")), the script hung indefinitely. It would block waiting for output, but nothing was ever returned.

The cause was C's standard I/O buffering. By default, stdout is line-buffered when connected to an interactive terminal, but fully buffered when connected to a pipe (which is what pwntools.process() creates). Because the initial printf prompt didn't flush immediately, the data sat in libc's internal 4096-byte stdio buffer waiting for a newline or buffer overflow. Meanwhile, Python was waiting on recvline(), and the C process was waiting on fgets(). A classic bidirectional pipe deadlock. 

/* The fix: disable stdout buffering completely at program start */
setvbuf(stdout, NULL, _IONBF, 0);

Alternatively, in targets where you cannot modify the source code, you can force interactive unbuffered mode using a pseudo-terminal (process("./vunl", stdin=PTY, stdout=PTY) in pwntools).

7 · Memory Leaks via Indexed Format Strings

Rather than manually typing out dozens of %lx tokens, I wrote an automated pwntools script that constructs indexed payloads using %i$lx or positional tags: 

from pwn import *

# Construct indexed payload to inspect the first 15 positions
parts = [f"{i}:%lx" for i in range(1, 16)]
payload = " ".join(parts)

p = process("./vunl")
p.sendline(payload.encode())

output = p.recvline().decode()
print(output)

p.close()

By printing the actual address of buf and &secet in the target binary, I was able to cross-reference the leaked hex values against real runtime memory addresses.

address fingerprinting On x86-64 Linux, different memory regions have distinct address prefixes:
• Stack pointers typically start with 0x7ffd... or 0x7fff...
• Shared libraries (libc, loader) and mmap regions start with 0x7f...
• Binary code and GOT slots (under PIE) start at lower bases like 0x55... or 0x56...
By looking at the prefixes in the leak output, I could tell immediately whether a given slot was a register residue, an internal printf frame pointer, or a stack variable from vunl().

8 · Honest Debugging Lessons

Looking back at where time was spent during this block, almost none of the issues were fundamental conceptual gaps. The real friction came from subtle boundary and control-flow mistakes around otherwise correct logic:

  • Inverted comparison operator: In the domain name validation loop, I had a comparison flipped on the label length check, which silently rejected valid single-character domains during testing.
  • Short-circuit order bug: In the DNS packet parser, I had an expression that evaluated an array index before verifying whether the cursor had exceeded the packet buffer length. The guard condition was placed after the access rather than before it.
  • Shadowed built-in variable: Accidentally naming a loop variable byte and later attempting to use standard bytes functions, which caused strange TypeError exceptions further down the function.

The takeaway was simple: guessing at bugs rarely works. Stepping through the execution path line by line with real inputs and printing intermediate buffer offsets caught every single one of these issues much faster than re-reading the code in circles.
