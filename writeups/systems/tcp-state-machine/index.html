1 · Core Mental Model: State over Best-Effort IP

IP is best-effort by design: packets can get dropped, duplicated, delayed, delivered out of order, or corrupted. User applications want a reliable, ordered, bi-directional byte stream. TCP creates that abstraction out of nothing more than a small set of counters and shared state maintained by the kernel at both ends.

The mechanics boil down to a few fundamental rules:

  • Every byte has a number: A segment's sequence number (seq) is the index of its first payload byte.
  • Cumulative acknowledgments: The ack number tells the sender what byte the receiver expects next, meaning every single byte before that number has arrived safely.
  • Retransmission buffer: The sender keeps unacknowledged bytes in its send buffer until an ACK moves past them. If a retransmit timer fires or three duplicate ACKs arrive (fast retransmit), it resends the missing data.
  • Hole handling: Out-of-order segments are buffered in a kernel queue until the missing prefix arrives. In Linux (include/linux/tcp.h), this is out_of_order_queue, implemented as a red-black tree keyed by sequence number.
  • Virtual byte consumption: SYN and FIN flags each consume exactly one sequence number, which is why their ACKs are seq + 1. A data segment containing n bytes consumes n sequence numbers, so its ACK is seq + n.
  • Independent streams: Each direction is completely separate. Each side chooses its own Initial Sequence Number (ISN) independently.
kernel state anchors (struct tcp_sock) In the Linux kernel, the core tracking variables live in struct tcp_sock:
• rcv_nxt: Next byte expected from peer (the ACK number sent in outgoing segments).
• snd_una: Oldest unacknowledged byte sent (left edge of the send window).
• snd_nxt: Next byte to be sent.

2 · The 3-Way Handshake & Kernel Queues

The handshake synchronizes sequence numbers between client and server: 

Client (Active)                               Server (Passive)
CLOSED                                        LISTEN
  |--- SYN, seq=X --------------------------->|  -> SYN_RECV
  |<-- SYN+ACK, seq=Y, ack=X+1 ---------------|
  |--- ACK, ack=Y+1 -------------------------->|  -> ESTABLISHED
SYN_SENT -> ESTABLISHED

The reason it takes three messages is mutual proof. Both endpoints need proof that the other side received its chosen ISN. The first two messages deliver the client's ISN and the server's ISN. But the third message is required to prove to the server that the client actually received Y. Without that final ACK, an attacker could spoof a SYN from an innocent IP, or a delayed duplicate SYN from an old connection could trick the server into allocating a live connection. With three steps, a stale SYN causes the unsuspecting client to reject the unexpected SYN+ACK with an RST.

Who actually does the work

One thing that took me a while to realize is that the handshake is driven entirely by the kernel, not by your userspace application code. Sockets and system calls merely interact with kernel queues:

When you call listen(fd, backlog), the kernel puts the socket into LISTEN and creates two queues:

  • SYN Queue (half-open): Holds connections in SYN_RECV that are waiting for the client's final ACK.
  • Accept Queue (fully open): When the final ACK arrives, the kernel creates a new socket struct in ESTABLISHED and moves it to the accept queue.

Calling accept() does not participate in the network handshake at all. It simply dequeues an already-established connection and returns a new file descriptor for it. If the client sends data before the server calls accept(), that data is already sitting in the newly created socket's receive buffer in the kernel.

file descriptor vs. kernel socket A file descriptor is just an integer index into a process's private fd table. A socket is an internal kernel object with its own state machine, buffers, timers, and 4-tuple. After accept(), the server owns two sockets: the listening socket (still in LISTEN) and the accepted connection socket (in ESTABLISHED). Furthermore, the accepted socket is the server's own endpoint, not the client's. The client has its own separate socket. Because kernel sockets are reference-counted, calling fork() or dup() duplicates the descriptor, and the underlying socket only closes when every referring fd is closed.

3 · Teardown: TIME_WAIT, CLOSE_WAIT & Orphans

Closing a connection takes four steps because TCP is full-duplex. Sending a FIN only means "I have no more data to transmit." It does not mean "I refuse to receive data." Each direction must be shut down independently. 

Active Closer (calls close())                Passive Closer
ESTABLISHED                                  ESTABLISHED
  --(send FIN)--> FIN_WAIT_1
                                               --(recv FIN / send ACK)--> CLOSE_WAIT
  --(recv ACK)--> FIN_WAIT_2
                                               --(app calls close() / send FIN)--> LAST_ACK
  --(recv FIN / send ACK)--> TIME_WAIT
                                               --(recv ACK)--> CLOSED
  --(wait 2*MSL)--> CLOSED

A helpful rule of thumb for TCP state names: the name describes what that socket is currently waiting for. SYN_SENT waits for a SYN+ACK, FIN_WAIT_1 waits for the ACK of its own FIN, FIN_WAIT_2 waits for the peer's FIN, CLOSE_WAIT waits for the local application to call close, and LAST_ACK waits for the final ACK.

The purpose of TIME_WAIT

Whichever endpoint initiates the teardown (sends the first FIN) ends up in TIME_WAIT. It remains there for twice the Maximum Segment Lifetime (2 * MSL, fixed in Linux at 60 seconds by TCP_TIMEWAIT_LEN). It serves two critical purposes:

  1. Repairing lost final ACKs: If the active closer's final ACK gets dropped in transit, the passive closer in LAST_ACK will time out and retransmit its FIN. If the active closer had destroyed its state immediately, it would respond to the retransmitted FIN with an RST, causing the peer's application to see a noisy ECONNRESET error instead of a clean EOF. By lingering in TIME_WAIT, it can absorb the retransmitted FIN, re-send the ACK, and restart the 2MSL timer.
  2. Draining stale segments: It guarantees that any delayed packets floating through the internet from the old connection die before the same 4-tuple can be allocated to a new connection.
TIME_WAIT vs. CLOSE_WAIT bugs
• TIME_WAIT pile-ups are normal for an active closer. The main friction is port exhaustion or the server restart problem, where bind() fails with EADDRINUSE because an old socket is still lingering. Setting SO_REUSEADDR before bind() tells the kernel to allow binding to the port even if existing connections are in TIME_WAIT.
• CLOSE_WAIT pile-ups are almost always an application bug. The kernel ACKed the peer's FIN, but it will never exit CLOSE_WAIT on its own because it assumes the local program might still want to write data. If the application forgets to call close(), the socket sits in CLOSE_WAIT forever, eventually leaking file descriptors until the process hits EMFILE.

If an application calls close() and exits while in FIN_WAIT_2, the socket becomes an orphan (no user space process owns the descriptor). Linux handles this by destroying orphaned FIN_WAIT_2 sockets after tcp_fin_timeout (default 60 seconds) silently, with no packet sent.

4 · Flow Control, Persist Timers & Congestion

TCP balances two distinct safety mechanisms: flow control (protecting the receiver from being overwhelmed) and congestion control (protecting the network from collapsing).

  • Flow Control (rwnd): The receiver advertises its available buffer space in the TCP window field. The sender cannot have more unacknowledged bytes in flight than this advertised receive window.
  • Zero-Window and the Persist Timer: If the receiver's buffer fills up, it advertises a window of 0. Once the receiver's application reads data, it sends an ACK with a non-zero window. But if that ACK is lost, both sides would deadlock indefinitely: the receiver waiting for data, the sender waiting for a window update. To prevent this, the sender runs a persist timer (tcp_probe_timer() in net/ipv4/tcp_timer.c) that sends zero-window probes with exponential backoff, forcing the receiver to reply with its current window size.
  • Congestion Control (cwnd): The sender maintains a congestion window (cwnd). The amount of data allowed in flight is min(rwnd, cwnd). During slow start, cwnd doubles every round trip until it hits ssthresh, after which it grows additively (one segment per RTT). Upon detecting loss, AIMD kicks in: three duplicate ACKs halve cwnd (multiplicative decrease), while an RTO timeout collapses cwnd back to 1 segment.
the flaw in classic loss-based congestion Traditional algorithms (like Reno or Cubic) assume that packet loss equals network buffer congestion. On wireless networks (cellular, WiFi), packets are frequently lost due to physical radio interference or handoffs rather than saturated routers. Treating random wireless loss as congestion causes needless throughput collapses. Modern rate-based algorithms like BBR (Bottleneck Bandwidth and RTT) decouple pacing from loss altogether.

5 · Security Mechanics: SYN Cookies, ISNs & RFC 5961

Because the TCP handshake allocates state before authenticating identity, it exposes several attack surfaces:

SYN Floods and SYN Cookies

In a standard handshake, the server allocates a struct request_sock and sets up retransmit timers upon receiving a SYN. An attacker sending thousands of SYNs with spoofed IP addresses easily fills the SYN queue, causing the kernel to drop legitimate connection attempts.

SYN cookies solve this by storing absolutely nothing. When the SYN queue overflows, the kernel calculates the server's initial sequence number (Y) as a keyed cryptographic hash of the client IP, client port, server IP, server port, a secret key, and a coarse timestamp, with a few bits encoding the MSS. The server sends this Y in the SYN+ACK and discards all memory of the packet.

When the client returns the final ACK, it sends ack = Y + 1. The server subtracts 1, recomputes the cryptographic hash from the incoming 4-tuple, and checks if it matches. If it does, the connection is instantiated on the spot.

syn cookie limitations SYN cookies prevent state exhaustion from blind off-path spoofers. However, they do not stop on-path attackers (who can observe Y directly), they break most negotiated TCP options (timestamps, window scaling, SACK) because there is nowhere to store them, and they cannot protect an overflowing accept queue (which is an application-level bottleneck).

ISN Randomization

If initial sequence numbers were predictable (such as incrementing counters), an off-path attacker could send a spoofed SYN to a server, predict what sequence number the server would pick in its SYN+ACK, and immediately forge the third ACK along with spoofed payload data (the classic Kevin Mitnick / Morris attack). Modern kernels (RFC 6528, secure_tcp_seq() in Linux) randomize ISNs using cryptographic hashing.

Blind RST Attacks and RFC 5961

A TCP RST segment aborts a connection immediately: no ACK is returned, unread data is dropped, and the connection transitions directly to CLOSED.

Historically, any RST whose sequence number fell anywhere within the receiver's current window was accepted. With a large receive window (e.g., 64 KB or window-scaled up to 1 GB), an off-path attacker guessing a 32-bit sequence number only needed a few thousand packets to blindly tear down long-lived sessions like BGP.

RFC 5961 fixed this: an RST is only accepted immediately if its sequence number exactly equals rcv_nxt. If the sequence number is inside the window but doesn't match rcv_nxt, the kernel drops the packet and sends a Challenge ACK back to the authentic peer. A blind attacker cannot see or answer the challenge, while the real peer will reply with an exact RST if it truly intended to abort.

6 · Loopback Lab: Observing Transitions in C

To prove these state transitions empirically, I wrote a minimal server (srv.c) and client (client.c) in C using only raw libc socket wrappers, running them across four tmux panes alongside tcpdump -i lo -n -S 'tcp port 6666' and watch -n 1 ss -tan. 

/* Server: reads data, then sleeps 90s without closing fd2 */
int fd2 = accept(fd1, (struct sockaddr *)&client_addr, &len);
while ((n = read(fd2, buf, sizeof(buf))) > 0) {
    printf("%s", buf);
}
printf("Sleeping 90s...\n");
sleep(90);
close(fd2);
/* Client: sends 100 bytes, closes socket immediately, sleeps 60s */
connect(fd1, (struct sockaddr *)&serv_addr, len);
write(fd1, "I'm client", 100);
close(fd1);  /* triggers active close */
printf("Sleeping 60s...\n");
sleep(60);

Timeline of What Happened

  1. Handshake & Data: The 3-way handshake ran cleanly. The client wrote 100 bytes, visible in tcpdump as a P. segment (PSH+ACK) with length 100, and the server ACKed it with ack = seq + 100.
  2. Active Teardown: The client called close(fd1), sending a FIN. The server kernel immediately responded with an ACK.
  3. State Pause: Running ss -tan showed the client socket in FIN-WAIT-2 and the server's accepted socket in CLOSE-WAIT, alongside the listening socket still in LISTEN.
  4. Orphan Timer Expiration (~60s): Because the client process closed its fd, the socket was an orphan. Exactly 60 seconds later, the client row vanished from ss -tan with zero packets sent on the wire.
  5. Server Process Exit (~90s): When the server process terminated, the kernel closed its leftover fd2. Because it was sitting in CLOSE_WAIT, the kernel sent a FIN to the client.
  6. The RST Reply: The client kernel received the FIN on port 6666, but because its orphaned socket had already vanished 30 seconds earlier, the client kernel replied with an RST. In accordance with RFC 793, the RST's sequence number matched the ACK field of the FIN it was answering.
  7. Teardown Complete: The server socket transitioned to CLOSED, and the listening socket disappeared cleanly without sending any packets.

7 · Mistakes Caught & Corrected

Writing down the predictions beforehand and verifying them against the kernel caught several flawed mental models I had walking into this week:

learning log: errors caught during analysis
  • Mistake: Assumed the file descriptor returned by accept() belonged to the client.
    Correction: It is the server's local handle for that connection. The client owns an entirely separate socket in its own kernel.
  • Mistake: Thought the LISTEN socket participates in teardown.
    Correction: The listening socket is completely untouched by individual connection closures.
  • Mistake: Assumed a socket in CLOSE_WAIT automatically moves to LAST_ACK after a timeout.
    Correction: The kernel never times out CLOSE_WAIT. Only the user application calling close() or process termination triggers the transition.
  • Mistake: Thought the client jumps straight to TIME_WAIT immediately upon calling close().
    Correction: The active closer must transition through FIN_WAIT_1 and FIN_WAIT_2, and only enters TIME_WAIT after receiving the peer's FIN.
  • Mistake: Drew TIME_WAIT --(recv FIN)--> FIN_WAIT_2.
    Correction: Receiving a retransmitted FIN in TIME_WAIT causes the kernel to re-send the ACK and restart the 2MSL timer; it stays in TIME_WAIT.
  • Mistake: Confused socket errors (ECONNREFUSED vs ECONNRESET).
    Correction: An RST on an established connection raises ECONNRESET. ECONNREFUSED only occurs when attempting to connect() to a port with no active listener.
  • Mistake: Believed SYN cookies were stored in a lightweight kernel table.
    Correction: SYN cookies are completely stateless; the state is embedded directly inside the 32-bit ISN.
  • Mistake: Used "process" and "socket" interchangeably.
    Correction: A process holds file descriptors. A socket is an independent kernel object governed by reference counts.
