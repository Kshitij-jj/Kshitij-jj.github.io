PLT / GOT — why does a function call even need all this

First confusion was just: why can't the compiler hardcode the address of puts? Turns out it can't, for two reasons — puts lives in libc, a separate file, so your binary doesn't contain it at all, and libc loads at a different address every run because of ASLR anyway. So the call can't point at a fixed address, it has to point at a pointer that gets filled in at runtime.

That pointer lives in the GOT (global offset table) — just an array of 8-byte slots in writable memory. Your code doesn't call puts directly, it calls through a tiny stub in .plt: 

puts@plt:
    jmp QWORD PTR [rip+0x2fe2]   ; jump to whatever address is stored in the GOT slot
confusion I had The [rip+...] thing confused me at first — it means "read 8 bytes FROM this address and jump there," not "jump to this address." Big difference. The stub reads the slot's contents, and those contents decide the behavior — there's no branching logic in the stub itself.

On the first call ever to puts: the GOT slot doesn't hold puts's real address yet. It holds the address of the next instruction in the same stub — basically a placeholder that says "not resolved yet, go run the resolver." That falls through to push <index> (so the resolver knows which function it's dealing with), then jumps to PLT0, which calls into ld.so's _dl_runtime_resolve. The resolver reads .rela.plt[index] (where to write the answer) and .dynsym / .dynstr (what symbol to look up as a string), finds the real address in libc, and writes it into the GOT slot.

Every call after that: the stub reads the slot, it's already the real libc address, jumps straight there. No resolver involved again. That's lazy binding.

Eager binding / -z now

If the resolver writes to the GOT at runtime, that page has to be writable for at least part of the process's life. The question that actually unlocked RELRO for me was: when exactly does it need to stop being writable?

wrong framing I started with My first instinct was "a function can get called any time, so there's no point locking it down." The GOT needs to stay writable only until every unresolved slot gets resolved — not indefinitely. If you force all symbols to resolve up front, the GOT becomes a pure read-only lookup table for the rest of the process's life.

That's what -z now (gcc -Wl,-z,now) does — forces all symbols to resolve before main() even starts, instead of waiting for first-use. Confirmed it two ways:

readelf -d shows FLAGS_1: NOW (declared intent, build-time fact). Then in GDB, breaking at main() and reading the actual GOT slot for puts with x/gx — without -z now it holds an address inside my own binary's .text (the stub fallback path). With -z now it already holds a real libc address before main ran at all. Empirically proved, not just read about it.

RELRO — Partial vs Full

Full RELRO is -z now (eager resolution) plus ld.so calling mprotect(.got.plt, size, PROT_READ) right before handing control to main(). Verified this with strace -e trace=mprotect — saw the actual syscall, PROT_READ only, on my binary's own GOT page. This is not something my own code calls — ld.so is the only thing that could possibly know "resolution just finished" and already has the address and size on hand, since it read PLTGOT / PLTRELSZ from .dynamic to do the resolving in the first place.

Partial RELRO (the default) keeps the GOT writable forever, because lazy binding needs ongoing writes to slots ld.so can't predict in advance. But stuff that's written once at build or load time and never touched again — .init_array, .fini_array, GOT[0..2] (the reserved bookkeeping slots) — still gets locked read-only, since none of that needs lazy binding to keep working. The linker deliberately puts these on a separate page from .got.plt, because mprotect only works at page granularity — you can't protect 24 bytes while leaving the other 8 on the same page writable.

mistake I made I initially read FLAGS_1: NOW backwards and called it Partial RELRO. NOW present means eager binding was requested — that's Full RELRO's prerequisite, not the opposite.

PIE / ASLR

PIE binaries have no fixed load address — every address in the file is an offset, and the kernel picks a random load base per region at execve() time, so real_address = load_base + file_offset.

GDB gotcha GDB disables ASLR by default for anything it launches (show disable-randomization → on). Spent a while confused why two GDB sessions of the same binary gave identical addresses — wasn't observing ASLR at all, just GDB's own reproducibility feature. Real ASLR only shows up running outside GDB, independently.

Entropy is /proc/sys/vm/mmap_rnd_bits — 28 bits on x86-64. 2^28 ≈ 268M possibilities sounds like a lot but isn't brute-forceable blind over a network — unless there's an info leak. One leaked pointer collapses the entire 28 bits to zero, since you can compute every other address in that region from one known offset (literally the same arithmetic I used by hand to find the GOT in GDB). That's the real lesson — ASLR is a tax on attackers with zero information, not a wall.

actually interesting fork()-based servers reuse the same randomized layout across every child (COW, same page table structure, inherited from one execve()), so an attacker gets a crash/success oracle against a fixed target across many connections — real technique, called BROP. exec()-per-connection servers re-roll ASLR every time, so there's no oracle to accumulate against.

NX and ret2libc

NX — the hardware no-execute bit — means data pages (stack, heap, GOT) can't be marked executable, so "write shellcode onto the stack, jump to it" doesn't work anymore. The CPU just refuses to fetch instructions from that page.

Doesn't close the door, just moves it. You can still corrupt a return address — NX says nothing about writing it, only about executing from wherever it points. If you can only point it at already-executable, already-existing code, the simplest useful target is a real libc function like system(), with the stack arranged so it gets your chosen argument. That's ret2libc.

correction I got system() is a libc function, not a syscall. Syscalls don't go through the GOT/PLT at all — they're a different mechanism entirely.

LD_PRELOAD — built a working malloc / free / realloc / calloc logger

LD_PRELOAD=/path/to/x.so is an environment variable ld.so reads before it even looks at the binary's own declared dependencies, and inserts x.so at the front of the library search order. So if x.so exports its own malloc, every call to malloc anywhere in the target program resolves to that version instead of glibc's — first-match wins, same rule as the GOT resolver, just applied to which library gets searched first.

Building an interposer — a logger that wraps malloc / free / realloc / calloc, logs the call, then still does the real allocation — ran into three separate recursion traps, each one genuinely surprising until traced through:

The obvious one: if my malloc()'s body calls malloc() again to get the real allocation, that just calls itself again (same first-match resolution rule), infinite recursion, stack overflow. Fix: dlsym(RTLD_NEXT, "malloc") — a real userspace function (not a syscall, just walks ld.so's own link_map) that explicitly means "find the next match after me."

Less obvious: my interposed malloc logging with printf() internally calls malloc() too (buffer for formatting), which resolves back to my malloc, which calls printf again — same recursion. Fix: snprintf into a stack buffer and raw write() syscall instead — no FILE* stream, no hidden allocation.

The one I'd never have guessed without being told: dlsym() itself, on glibc, internally calls calloc() for its own bookkeeping the first time it resolves a symbol. So the very first call to my interposed calloc triggers dlsym, which calls calloc again, which — since real_calloc isn't set yet — tries to resolve via dlsym again. Fixed with a static "currently inside dlsym" flag that, when set, serves a few zeroed bytes from a small preallocated static buffer instead of recursing. Had to separately fix integer overflow in total * size (classic calloc overflow bug class, real CVEs from exactly this) and get the check-before-commit ordering right — compute nothing, touch no shared state, until both the overflow check and the capacity check pass. 

/* dlsym bootstrap buffer — avoids calloc recursion during dlsym init */
static char   dlsym_buf[4096];
static int    dlsym_in_use = 0;

void *calloc(size_t nmemb, size_t size) {
    if (dlsym_in_use) {
        /* serve from static buffer; size is always tiny during dlsym */
        return memset(dlsym_buf, 0, sizeof(dlsym_buf));
    }
    if (!real_calloc) {
        dlsym_in_use = 1;
        real_calloc = dlsym(RTLD_NEXT, "calloc");
        dlsym_in_use = 0;
    }
    /* overflow check before anything else */
    if (nmemb && size > SIZE_MAX / nmemb) { errno = ENOMEM; return NULL; }
    void *ptr = real_calloc(nmemb, size);
    log_call("calloc", ptr, nmemb * size);
    return ptr;
}

Tested the whole thing against /bin/ls — worked, real log output interleaved with ls's actual directory listing. The interleaving itself taught me something unplanned: my write() is unbuffered (fires immediately, syscall every time), but ls's own output goes through buffered printf / streams (batches, flushes on buffer full, explicit flush, or exit). That's why the log lines and the real ls output don't interleave character-by-character — they show up as separate chunks depending on when each side actually flushes.

still TODO — being honest The spec also wants bin classification (which free-list a chunk would land in — fast / tcache / large / mmap) and double-free detection. Built bin classification separately in a chunk inspector that reads raw chunk headers and decodes safe-linking by hand, but haven't merged it into the interposer yet, and double-free detection isn't built. Turns out "walk the tcache and check if the pointer's already there" is actually weaker than glibc's own built-in tcache key check, which itself has a known gap (fastbin overflow past tcache's 7-per-bin cap has no key field at all). The real fix needs the interposer to keep its own independent bookkeeping of freed-but-not-reallocated pointers — queued up for later.

mmap / mprotect / W^X

mprotect only changes permissions on memory that's already mapped by something else. mmap can create a brand new mapping from nothing — including anonymous mappings with no backing file at all (MAP_ANONYMOUS), which is what most of those blank-filename rw-p rows in /proc/<pid>/maps actually are.

The "a page is writable XOR executable, never both" rule is called W^X. JIT compilers (V8, HotSpot, etc.) legitimately need to write fresh machine code and then run it — they do this safely in two steps: mmap with PROT_READ|PROT_WRITE, write the bytes, then mprotect to flip it to PROT_READ|PROT_EXEC right before jumping in. At no point is the page both writable and executable.

red flag to watch for If you ever see a standing rwxp region in a real process's memory map, that's either sloppy JIT / debugger-instrumentation design or active exploitation — worth investigating either way, since it completely collapses NX's whole purpose the moment an attacker gets any write into it.
